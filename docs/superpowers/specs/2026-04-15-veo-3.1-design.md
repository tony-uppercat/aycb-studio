# Google Veo 3.1 — Video Generation Provider

**Date:** 2026-04-15
**Status:** Draft (pending user review)

## Goal

Add Google Veo 3.1 as a fourth video-generation provider in the Generate Video node, alongside the existing Atlas Cloud, fal.ai, and PiAPI providers. Use the native Vertex AI API (reusing the existing GCP project already configured for Imagen edit), not a reseller.

## Motivation

Veo 3.1 is Google's current flagship video model. It offers native audio, reference-image grounding (up to 3), last-frame interpolation, and competitive quality. Vertex AI is the lowest-latency, authoritative path for Veo access and piggybacks on infrastructure the project already has in place for Imagen.

## Scope

**In scope:**
- New backend client `src/vertex_video_gen.py` with the same public surface as `atlas_video_gen.py` / `fal_video_gen.py` (`submit_text_to_video`, `submit_with_refs`, `get_result`, `wait_for_completion`).
- Extract the cached `_get_vertex_client()` helper (currently private in `src/routers/image_edit.py`) into a new shared module `src/vertex_client.py` so both Imagen edit and Veo video reuse one cached `genai.Client`.
- Backend router dispatch: `if model.startswith("vertex-"): ...` in `src/routers/generate.py`, plus `provider == "vertex"` branch in `/api/generate/video/status/{request_id}`.
- Frontend model registry: two new entries (`vertex-veo-3.1`, `vertex-veo-3.1-fast`) in `VIDEO_MODELS` in `useGenerateVideo.ts`.
- Frontend provider button: new `{ id: 'vertex', label: 'Veo' }` in `GenerateVideoNode.tsx`.
- Local save: when Vertex polling returns a completed video, the backend downloads the bytes via the SDK, writes them to `shared/Media/veo_<request_id>.mp4`, and returns a URL of shape `/media/veo_<request_id>.mp4`. This URL is already served by the Review Hub static mount (`src/review_hub/app.py` mounts `/media` → `settings.media_dir`). The frontend passes this URL to the existing `bridgeVideo()` flow unchanged.

**Out of scope:**
- No new API-key setting — Veo uses `settings.gcp_project` (already configurable from Settings > GCP).
- No Veo 2.x support — Veo 3.1 only.
- No reference-video input path — Veo I2V supports first-frame image only. Multi-image refs use `reference_images` (style/subject grounding), not frame interpolation.
- No audio-URL input — Veo generates audio internally; the existing `audio-ref` input slot is ignored for Veo, and a warning is logged server-side (mirroring Atlas behavior).

### `vertex_video_gen.py` (new, ~220 lines)

Shape mirrors `atlas_video_gen.py` so the router can dispatch uniformly.

        "qualities": ["720p"],

**Submit (async):**
- `submit_text_to_video(api_key, model_id, prompt, aspect_ratio, duration, quality, **_)` — ignores `api_key` (Vertex uses GCP creds), logs a notice if passed.
  - Calls `client.models.generate_videos(model=..., prompt=..., config=GenerateVideosConfig(aspect_ratio=..., duration_seconds=..., resolution=..., number_of_videos=1, generate_audio=True, person_generation="allow_adult"))`.
  - Returns `{"request_id": operation.name, "status": "pending"}`.
- `submit_with_refs(api_key, model_id, prompt, ref_image_bytes, ref_video_bytes, audio_url, aspect_ratio, duration, quality, **_)`:
  - `ref_video_bytes` ignored with warning.
  - `audio_url` ignored with warning.
  - If 1 image only → `image=types.Image(image_bytes=...)` (I2V first frame).
  - If 2 images → `image=<first>` + `config.last_frame=types.Image(image_bytes=<second>)` (first-last interpolation).
  - If 3+ images → `config.reference_images=[types.VideoGenerationReferenceImage(image=..., reference_type="asset") for img in images[:3]]` (subject/style grounding).
  - All branches call the same submit helper and return `{"request_id": operation.name, "status": "pending"}`.

SDK calls run on the event loop via `asyncio.to_thread` because `google-genai` is sync-only.

**Poll / save (async):**
- `get_result(api_key, request_id) -> {"request_id", "status", "url", "error"}`:
  - `operation = client.operations.get(request_id)`.
  - If `not operation.done` → `{"status": "processing", "url": "", "error": ""}`.
  - If `operation.error` → `{"status": "failed", "error": str(operation.error)}`.
  - If done and has `operation.response.generated_videos`:
    - Take `[0].video`.
    - `client.files.download(file=video)` to hydrate bytes.
    - `video.save(settings.media_dir / f"veo_{safe_id}.mp4")` where `safe_id` is `request_id` with `/` → `_`.
    - Return `{"status": "completed", "url": f"/media/veo_{safe_id}.mp4", "error": ""}`.
- `wait_for_completion(api_key, request_id, poll_interval=10, timeout=600)` — same shape as existing providers.

The `request_id` is the full operation resource name (e.g. `projects/X/locations/us-central1/publishers/google/models/veo-3.1-generate-preview/operations/abc`). It can contain slashes, which are safe as a query param; the filename derived from it slash-escapes.

## Data Flow

```
User clicks Run
  ↓
useGenerateVideo.run() pulls prompt + refs, detects mode
  ↓
POST /api/generate/video {model=vertex-veo-3.1, ...}
  ↓
_generate_video_vertex → vertex_video_gen.submit_with_refs
  ↓
Vertex AI generate_videos → Operation
  ↓
Response {request_id: "projects/.../operations/xyz", status: "pending"}
  ↓
Frontend startPolling → GET /api/generate/video/status/{request_id}?provider=vertex
  ↓
vertex_video_gen.get_result
  → operation done? no → {"status": "processing"}
  → operation done? yes → download bytes, save to shared/Media/veo_<id>.mp4
                        → {"status": "completed", "url": "/media/veo_<id>.mp4"}
  ↓
Frontend bridgeVideo(url, meta) — existing flow, unchanged
```

## Error Handling

- `settings.gcp_project` unset → `ValueError` in `get_vertex_client` → router maps to HTTP 400 with clear message.
- Vertex API rejection (quota, content policy) → `VertexVideoGenError` → HTTP 422 with Vertex's message stripped of sensitive headers.
- Operation returns an error object → `get_result` returns `{"status": "failed", "error": ...}`; polling loop surfaces it.
- Local save failure (disk full, permission) → raise `VertexVideoGenError`; frontend shows the message and stops polling.
- No `except: pass` anywhere — every failure is logged via `_log(...)` from `src/shared.py`.

## Testing

New file `tests/test_vertex_video_gen.py`:
- `get_model_info` — known/unknown IDs.
- `submit_*` — patches `get_vertex_client` to return a mock whose `models.generate_videos` returns a fake operation; asserts the config passed (model name, aspect_ratio, duration_seconds, resolution, generate_audio, reference_images count, last_frame presence).
- `get_result` — three states: not done, done+error, done+success (the success case patches `files.download` + `video.save` and asserts the output path and returned URL).
- Error mapping: missing GCP project raises `ValueError` at submit time.

Router integration: one new case in the existing test file that covers `/video/status/{id}?provider=vertex` routing to `vertex_video_gen.get_result` (mocked).

Existing test suite (98 backend + 115 frontend) must pass unchanged after refactoring `_get_vertex_client` out of `image_edit.py`.

## Risks / Open Questions

1. **SDK version.** `google-genai` must be recent enough to expose `veo-3.1-generate-preview` and `last_frame`. Plan will pin a minimum version in `pyproject.toml` during implementation; if the current installed version is too old, upgrade during setup.
2. **`resolution` parameter.** The SDK accepts `resolution` in `GenerateVideosConfig` but some Veo variants may ignore it. If 1080p requests produce 720p output silently, document and/or hide the 1080p option.
3. **Person generation.** Defaulting to `allow_adult` because Antonio generates commercial content. Flag if Vertex region (`us-central1`) blocks this — fallback to `dont_allow` with log warning.
4. **Filename safety.** Operation names contain slashes (`projects/.../operations/xyz`). Escape via `request_id.replace("/", "_")` before using as filename, but keep the raw `request_id` as the status-polling key.
